# 모든 변경은 담당 브랜치에서 검증한 뒤 PR로 병합한다.

| 항목 | 규칙 | 결과값 |
|---|---|---|
| 시작 브랜치 | `develop`에서 작업 브랜치를 만든다. | `feature/`, `fix/`, `chore/`, `docs/`, `hotfix/` 브랜치 |
| 담당 범위 | 담당 폴더 밖의 수정은 `integration-agent`와 API 계약을 먼저 확인한다. | 변경 영향 범위가 명확한 PR |
| PR 대상 | 일반 작업은 `develop`, 운영 반영은 `develop → main`으로 연다. | 스테이징 PR 또는 운영 PR |
| 제목 | `[영역] 무엇을 바꿨는지`로 작성한다. | 예: `[frontend] 콘텐츠 패키지 카드 추가` |
| 본문 | 목적, 영향 영역, 검증 결과, 환경 변수·DB 변경만 적는다. | 짧고 재현 가능한 변경 설명 |
| 검증 | 수정한 영역의 최소 검증을 실행한다. | 화면 확인 / Kotlin 컴파일 / 자동화 안전 실행 |
| AI 기능 | 모델, 토큰·비용, 도구, 실행 이력 기록 여부를 확인한다. | AI 운영 센터에 남는 실행 기록 |
| 비밀값 | API 키, OAuth 토큰, 개인 데이터, `data/`, `config/.env`를 포함하지 않는다. | 안전한 커밋 |
| 병합 | 승인·검증 후 병합하고, 운영 PR은 배포 결과를 확인한다. | `develop` 또는 `main` 반영 완료 |
| 긴급 수정 | `hotfix/`에서 `main`으로 먼저 반영한 뒤 `develop`에도 되돌려 합친다. | 운영·개발 브랜치 동기화 |
